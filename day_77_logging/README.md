# Structured Logging, Log Levels and Correlation IDs

## 1. Technical Scope

This project implements a structured logging system across Python, JavaScript, C++17, Java 17 and PostgreSQL.

The implementations cover three connected observability mechanisms:

- Structured logging represents application events as machine-readable records.
- Log levels classify events according to their severity and operational importance.
- Correlation IDs connect events generated by different components during the processing of the same request.

The implementations demonstrate application instrumentation, event serialization, context propagation, filtering, sensitive-data protection, concurrent execution and log analysis.

## 2. Structured Logging

### 2.1 Concept

Structured logging represents an event using named fields instead of relying exclusively on unstructured text.

A conventional log entry might contain:

`Payment processing failed for customer CUSTOMER-101`

A structured event separates its components:

| Field | Example |
|---|---|
| timestamp | 2026-11-16T09:15:00Z |
| level | ERROR |
| service | payment-service |
| message | Payment processing failed |
| correlation_id | CORR-1001 |
| request_id | REQ-1001 |
| customer_id | CUSTOMER-101 |
| error_code | GATEWAY_TIMEOUT |

The structured representation makes individual attributes searchable, filterable and suitable for aggregation.

### 2.2 Event structure

The implementations use a common conceptual event model:

`LogEvent = Timestamp + Severity + Service + Message + Context + Attributes`

The timestamp identifies when an event occurred.

The severity indicates its operational importance.

The service identifies the application component responsible for the event.

The message describes the event in human-readable form.

The context connects the event to a request or distributed operation.

The attributes contain additional structured information.

### 2.3 JSON serialization

JSON is used as the primary interchange format.

The Python formatter, JavaScript logger, C++ encoder and Java serializer produce machine-readable event representations.

Important serialization requirements include:

- Correct quotation-mark escaping.
- Correct handling of newline characters.
- Consistent field names.
- Valid timestamp representations.
- Explicit null handling.
- Safe conversion of exceptions.
- Prevention of circular-reference failures where applicable.

Structured events should retain a consistent schema across application versions.

## 3. Log Levels

Log levels classify events according to severity.

The project implements five standard levels.

| Level | Severity | Purpose |
|---|---:|---|
| DEBUG | 10 | Detailed diagnostic information |
| INFO | 20 | Normal application operations |
| WARNING | 30 | Potential operational problems |
| ERROR | 40 | Failed operations |
| CRITICAL | 50 | Severe application or service failures |

### 3.1 DEBUG

DEBUG records internal execution details.

Examples include:

- Request processing stages.
- Configuration loading.
- Validation decisions.
- Diagnostic state transitions.

DEBUG logging is useful during development and troubleshooting but can produce substantial event volumes.

### 3.2 INFO

INFO records expected application activity.

Examples include:

- Application startup.
- User authentication success.
- Order creation.
- Payment authorization.
- Transaction completion.

These events establish an operational history without necessarily indicating a problem.

### 3.3 WARNING

WARNING identifies abnormal conditions that do not necessarily prevent execution.

Examples include:

- Low inventory.
- Approaching resource limits.
- Retry operations.
- Delayed external dependencies.

Warnings help identify developing operational problems.

### 3.4 ERROR

ERROR indicates that an operation has failed.

Examples include:

- Payment gateway rejection.
- Database connection failure.
- Invalid application requests.
- Failed transaction processing.

An error does not necessarily imply that the complete application has stopped functioning.

### 3.5 CRITICAL

CRITICAL represents a severe condition requiring immediate attention.

Examples include:

- Essential service unavailability.
- Failure of a critical dependency.
- System-wide processing interruption.
- Loss of an essential operational capability.

### 3.6 Log filtering

A logging threshold determines the minimum severity accepted by a logger.

For a threshold of INFO:

- DEBUG is suppressed.
- INFO is accepted.
- WARNING is accepted.
- ERROR is accepted.
- CRITICAL is accepted.

Filtering reduces unnecessary processing, storage consumption and event volume.

It is important to distinguish application-level filtering from centralized collection policies. An event suppressed before transmission cannot be recovered by a downstream logging platform.

## 4. Correlation IDs and Request IDs

### 4.1 Correlation ID

A correlation ID identifies a logical operation across multiple application components.

Consider an online order:

`Client → Order Service → Payment Service → Inventory Service`

Each service generates independent log events.

Without a common correlation identifier, investigators may need to search by approximate timestamps, customer identifiers or transaction values.

A correlation ID provides a shared reference.

Example:

`CORR-ORDER-1001`

The same correlation identifier is propagated through the participating services.

This allows related events to be retrieved and analyzed together.

### 4.2 Request ID

A request ID identifies an individual request or processing attempt.

A correlation ID can represent a larger business operation, while request IDs distinguish individual requests within that operation.

For example:

| Operation | Correlation ID | Request ID |
|---|---|---|
| Initial order request | CORR-1001 | REQ-1001 |
| Payment request | CORR-1001 | REQ-1002 |
| Inventory request | CORR-1001 | REQ-1003 |

The identifiers have related but distinct purposes.

### 4.3 Distributed context propagation

A correlation identifier must be transmitted between services.

Common propagation mechanisms include:

- HTTP request headers.
- Message queue metadata.
- RPC metadata.
- Background job context.
- Explicit method parameters.

The implementations demonstrate different approaches.

| Language | Context mechanism |
|---|---|
| Python | `ContextVar` |
| JavaScript | `AsyncLocalStorage` |
| C++17 | Explicit `LogContext` parameters |
| Java 17 | Immutable `LogContext` records |
| PostgreSQL | Correlation registry and UUID references |

Python's `ContextVar` supports context-aware execution, including asynchronous task contexts.

JavaScript's `AsyncLocalStorage` maintains context across supported asynchronous execution paths.

C++ uses explicit context passing, which makes dependencies visible at function boundaries.

Java uses immutable records to make context propagation explicit and suitable for concurrent execution.

The database maintains relationships between parent and child correlation contexts.

### 4.4 Correlation versus distributed tracing

Correlation IDs are not equivalent to distributed tracing identifiers.

A correlation ID groups related application events.

Distributed tracing introduces additional concepts:

- Trace ID: identifies a distributed trace.
- Span ID: identifies an individual operation within a trace.
- Parent span ID: identifies the operation that initiated another span.

The PostgreSQL implementation includes optional trace and span fields to demonstrate this distinction.

Correlation-based log searching remains useful even when a complete tracing system is unavailable.

## 5. Python Implementation

The Python script implements a reusable application logging system using standard-library components.

### 5.1 Main components

| Component | Responsibility |
|---|---|
| `LogLevel` | Severity definitions |
| `logging_context` | Correlation and request context |
| `redact` | Sensitive-data protection |
| `StructuredFormatter` | JSON event serialization |
| `create_logger` | Logger configuration |
| `ApplicationLogger` | Application-facing logging interface |
| `PaymentService` | Example business workflow |
| `analyze_log_file` | Log-file analysis |

### 5.2 ContextVar

`ContextVar` maintains identifiers within an execution context.

The context manager temporarily establishes correlation and request identifiers.

It restores the previous values after execution, including when an exception occurs.

This prevents request metadata from leaking into subsequent operations.

### 5.3 StructuredFormatter

The formatter converts Python logging records into JSON.

It captures:

- Timestamp.
- Severity.
- Logger name.
- Message.
- Correlation ID.
- Request ID.
- Module.
- Function.
- Source line.
- Process and thread identifiers.
- Additional attributes.
- Exception information.

### 5.4 File handling

The implementation uses `RotatingFileHandler`.

The configured file size is 5 MB, with five backup files.

Rotation limits the size of an individual log file.

This is useful for local application logging, although production deployments should also consider centralized collection, retention and disk-space monitoring.

### 5.5 Log analysis

The analysis function reads JSON Lines records.

It calculates:

- Total valid events.
- Invalid records.
- Events by severity.
- Unique correlation identifiers.

The function processes records incrementally instead of loading the entire file into memory.

## 6. JavaScript Implementation

The JavaScript implementation uses Node.js asynchronous execution features and event-driven monitoring.

### 6.1 AsyncLocalStorage

`AsyncLocalStorage` propagates request context across supported asynchronous operations.

The example uses nested asynchronous execution to demonstrate that child operations retain the original correlation identifier.

This is important for services using promises, asynchronous functions and background operations.

### 6.2 EventEmitter

`StructuredLogger` extends `EventEmitter`.

Whenever an event is produced, it emits a `log` event.

The monitoring component listens for these events and maintains severity counters.

This separates event production from monitoring logic.

### 6.3 FileTransport

`FileTransport` provides asynchronous persistence.

A promise queue serializes file operations, reducing the possibility of concurrent writes interleaving.

The transport also exposes a close operation that waits for pending writes.

File write failures are propagated to the caller.

### 6.4 Sampling

The logger supports configurable sampling.

A sampling rate of 1 accepts every eligible event.

A sampling rate of 0 suppresses sampled informational events.

Sampling is applied to DEBUG and INFO events in this implementation, while more severe events are retained.

Sampling is useful when high-volume diagnostic events create excessive storage or processing costs.

It should not be applied indiscriminately to audit or security events.

### 6.5 Circular references

The recursive sanitizer tracks visited objects using a `WeakSet`.

Circular references are represented by a marker instead of causing infinite recursion during serialization.

This provides defensive behavior when application attributes contain complex object structures.

## 7. C++17 Implementation

The C++ program implements a structured logging engine alongside a repository-governance eligibility example.

The repository scenario demonstrates how operational events can be recorded when a complex policy evaluation succeeds or fails.

### 7.1 Domain structures

The implementation defines:

- `LogEvent`
- `LogContext`
- `LogMetrics`
- `StatusCheck`
- `ReviewDecision`
- `BranchPolicy`
- `PullRequest`
- `EligibilityResult`

These structures separate event information from application-specific business state.

### 7.2 JSON encoding

`JsonEncoder` handles JSON escaping and event serialization.

The encoder also checks attribute names against a sensitive-field list.

The implementation uses string-valued attributes to maintain a simple dependency-free representation.

### 7.3 Thread safety

A mutex protects complete output operations.

This prevents log lines from multiple threads from being interleaved.

The example uses an independent context for a background thread.

The caller explicitly provides correlation and request identifiers rather than depending on implicit thread-local state.

### 7.4 Governance integration

The merge eligibility engine evaluates:

- Pull Request state.
- Draft status.
- Merge conflicts.
- Resolved review conversations.
- Eligible reviewer decisions.
- Required approvals.
- Required status checks.

The logging engine records the results.

This demonstrates how structured logs can make policy decisions observable and auditable.

## 8. Java 17 Implementation

The Java implementation models logging as an enterprise service with explicit domain types and policy objects.

### 8.1 Immutable records

The implementation uses Java records for:

- `LogContext`
- `LogEvent`
- `LoggingPolicy`

Records provide concise data structures with generated accessors and value-oriented behavior.

The log event copies its attributes into an unmodifiable map.

This prevents external modification of the event's top-level attribute collection after construction.

### 8.2 LogSink interface

The `LogSink` interface separates event generation from output destinations.

The supplied `ConsoleSink` writes JSON records to standard output or standard error according to severity.

Additional destinations can implement the same interface without changing the core logging service.

### 8.3 LoggingPolicy

The policy object controls:

- Minimum severity.
- Excluded services.
- DEBUG event inclusion.

This separates configuration and governance rules from event serialization.

### 8.4 LoggingMetrics

`ConcurrentHashMap` and `LongAdder` support concurrent event counting.

These structures are suitable for concurrent workloads where multiple threads update severity counters.

### 8.5 Enterprise service

The `OrderService` generates structured events during order creation.

It records the beginning and completion of processing.

Invalid amounts are rejected before order creation and can be logged through the exception-handling interface.

## 9. PostgreSQL Implementation

The database implementation provides a relational model for structured log storage and analysis.

### 9.1 Entity relationships

The principal relationship is:

`Applications → Logging Policies`

`Log Levels → Log Events`

`Applications → Log Events`

`Correlation Contexts → Log Events`

`Correlation Contexts → Child Correlation Contexts`

`Log Events → Monitoring Views`

### 9.2 Main tables

| Table | Purpose |
|---|---|
| `log_levels` | Severity definitions |
| `applications` | Registered applications |
| `correlation_contexts` | Distributed operation relationships |
| `log_events` | Structured event storage |
| `logging_policies` | Severity and retention configuration |

### 9.3 JSONB

The `attributes` column uses PostgreSQL JSONB.

JSONB supports structured event attributes and indexing.

The GIN index supports suitable containment and key-existence queries.

Relational columns are retained for frequently filtered fields such as:

- Application.
- Severity.
- Correlation ID.
- Request ID.
- Timestamp.

This avoids placing every searchable attribute inside one large JSON document.

### 9.4 Constraints and validation

The schema uses:

- Primary keys.
- Foreign keys.
- Unique constraints.
- Check constraints.
- JSONB type validation.
- Severity references.
- Retention limits.

The `write_log_event` function validates application identity, severity, message and attributes before insertion.

The trigger performs an additional validation and redaction step.

### 9.5 Correlation registry

The `correlation_contexts` table represents parent-child relationships.

A root operation can initiate downstream service operations.

The child contexts reference their parent through a self-referencing foreign key.

The `correlation_event_summary` view aggregates event counts and identifies operations containing errors.

### 9.6 Database functions and procedures

`redact_log_attributes` protects designated sensitive JSON fields.

`write_log_event` performs validated event insertion.

`validate_log_event` enforces additional event-level checks.

`purge_expired_logs` removes records according to application retention policies.

These operations demonstrate the distinction between event creation, integrity enforcement and lifecycle management.

### 9.7 Transactions

The SQL script includes transactional insertion of related events.

The transaction ensures that the database changes are committed together or rolled back together.

This provides atomicity for the database operations within that transaction.

It does not make database logging automatically atomic with an external business transaction or message broker.

For that requirement, a transactional outbox pattern or another coordinated delivery mechanism would be necessary.

## 10. Security and Privacy

Logging systems can unintentionally become repositories of sensitive information.

The implementations include basic protection against recording designated sensitive fields.

### 10.1 Sensitive attributes

Fields requiring protection include:

- Passwords.
- Access tokens.
- API keys.
- Authorization values.
- Secrets.
- Credit card information.

Sensitive values are replaced with `[REDACTED]`.

### 10.2 Additional security considerations

Field-name redaction is a basic safeguard, not a complete data-loss prevention system.

Production implementations should also consider:

- Secret detection within free-text messages.
- Personally identifiable information.
- Authentication headers.
- Session identifiers.
- Database connection strings.
- Exception messages containing credentials.
- Access controls for log readers.
- Encryption in transit and at rest.
- Audit records for privileged access.
- Restricted retention and deletion policies.

Logs should not contain authentication credentials or unnecessary personal information.

### 10.3 Log injection

Untrusted input can contain newlines, quotation marks or other special characters.

Improper serialization may produce misleading log entries or invalid JSON.

The JSON encoders escape relevant characters.

Structured attributes should be serialized rather than concatenated into raw log output.

## 11. Operational Performance

Logging has measurable performance and storage costs.

| Mechanism | Performance consideration |
|---|---|
| Structured serialization | CPU and memory consumption |
| DEBUG logging | Increased event volume |
| File persistence | Disk I/O |
| Async file writes | Queue management |
| Correlation propagation | Context management overhead |
| JSONB indexes | Storage and insertion overhead |
| Log aggregation | Network and processing costs |
| Retention | Storage reclamation and maintenance |

### 11.1 High-volume applications

A production logging architecture should separate application execution from centralized log processing where necessary.

An asynchronous transport can reduce the time spent waiting for storage operations.

It must also define queue limits, backpressure and behavior during destination failures.

### 11.2 Retention and partitioning

The PostgreSQL implementation provides retention configuration and a cleanup procedure.

For high-volume systems, time-based table partitioning is preferable to maintaining one indefinitely growing table.

Partition maintenance, archive policies and index sizes should be evaluated against actual event volume.

### 11.3 Log loss

Asynchronous logging can introduce event-loss risks during:

- Process termination.
- Queue overflow.
- Storage failure.
- Network interruption.
- Application crashes.

Critical audit events may require durable delivery and explicit acknowledgment rather than best-effort logging.

## 12. Important Distinctions

| Concept | Meaning |
|---|---|
| Structured logging | Machine-readable representation of events |
| Log level | Severity classification |
| Correlation ID | Identifier connecting related operations |
| Request ID | Identifier for an individual request |
| Trace ID | Identifier for a distributed trace |
| Span ID | Identifier for an individual traced operation |
| Log filtering | Suppression of events below a configured threshold |
| Log sampling | Selective retention of eligible events |
| Log aggregation | Combining events for analysis |
| Log retention | Defining how long records remain available |
| Redaction | Removing or replacing sensitive information |

These concepts solve different problems and should be implemented as complementary mechanisms.

### Python

Requirements:

- Python 3.10 or later.
- Standard library only.

Execution:

`python structured_logging.py`

The script creates a `logs` directory and writes JSON Lines records to `logs/application.jsonl`.

### JavaScript

Requirements:

- Node.js 18 or later.
- Standard library only.

Execution:

`node structured_logging.js`

The application writes structured records to the console and `logs/application.jsonl`.

- C++17-compatible compiler.

Compilation:

`g++ -std=c++17 -O2 -pthread structured_logging.cpp -o structured_logging`

`psql -U postgres -d postgres -f structured_logging.sql`

## 15. Limitations

The implementations intentionally demonstrate core logging mechanisms without claiming to provide a complete centralized observability platform.

Important limitations include:

- The Python implementation uses local rotating files rather than remote log aggregation.
- The JavaScript file transport does not implement production-grade queue limits or automatic rotation.
- The C++ encoder uses string-valued attributes rather than a complete dynamically typed JSON model.
- The Java implementation demonstrates a console sink rather than durable distributed storage.
- The PostgreSQL schema is not partitioned by time.
- Correlation propagation is demonstrated locally and through explicit context structures, not through a complete network protocol implementation.
- Sampling and filtering policies require further governance for audit-sensitive applications.
- Database retention does not replace backup, archival or legal preservation policies.

A production implementation must define event schemas, context propagation contracts, access controls, failure handling, retention and operational monitoring consistently across participating services.
